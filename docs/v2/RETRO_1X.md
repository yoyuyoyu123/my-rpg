# 1.x 复盘：哪些目标在现有方法上做不到

日期：2026-10-28  
范围：v1-final 为止的全部历史（2026-03-24 起，149 个提交）、记忆中的用户反馈、[1.x 基线](./BASELINE_1X.md)、`research/interactive_narrative_systematic_review.md`。

本文区分三种陈述：**【事实】** 有提交或数据为证；**【判断】** 我基于事实的推断；**【假设】** 待验证的新方法。

---

## 1. 判别框架

一个叙事目标能不能"靠写更好的提示词"做成，取决于三个问题：

1. **定义清楚吗？** 能不能写出一个判定条件，让两个人对同一段正文给出相同结论。
2. **谁能验证？** 程序 / 模型 / 只有玩家本人。
3. **模型的训练偏好是顺着它还是逆着它？** 对话模型被训练得乐于配合、措辞稳妥、偏向高概率表达。

按这三问，1.x 的目标落进五类。前两类可做，后三类在"只改提示词"的方法下做不到或不可持续。

| 类别 | 特征 | 1.x 的出路 |
|---|---|---|
| A 可程序化 | 定义清楚 + 程序能验 | 交给程序（已大体做到） |
| B 工程脆弱 | 定义清楚，但实现方式脆弱 | 换实现方式即可 |
| C 逆训练偏好 | 定义大致清楚，只有模型能做，但模型天生往反方向走 | 提示词收益递减，需要结构性方法 |
| D 口味问题 | 定义模糊，只有玩家能判 | 规则写不出来，需要意图数据 + 玩家信号 |
| E 自相矛盾 | 多个目标的要求互相冲突 | 不是难，是不可能同时满足；靠产品决策解决 |

## 2. 逐类复盘

### A 可程序化——1.x 做对了的部分

角色属性、资源、背包、检定、事实、事件、承诺、NPC 知情范围。

- 【事实】演进方向一直是"从提示词搬进程序"：07-10 JS 权威状态 → 08-18 事实库与矛盾拦截 → 08-20 状态结算搬到后端（"模型只能申报，生不生效由程序说了算"）→ 08-24 风险检定程序化。
- 【事实】确定性回放 10/10 通过；这部分是 1.x 最稳的地方。
- 【判断】这类问题的剩余难点不在程序侧，而在**从散文里抽取事实**（记忆 Agent 每回合 0.74 次调用）——抽取错了，账本就记错了。属于 B 类。

### B 工程脆弱——方法本身可行，实现方式不对

| 目标 | 1.x 的实现 | 脆在哪 | 【事实】证据 |
|---|---|---|---|
| 同一次生成既写小说又输出机器协议 | 正文末尾附【STATE】块 | 截断就丢协议；模型会改格式 | 039270b "撞上输出上限不再整段丢弃：保正文、剥半截协议块" |
| 规则全部写在一个大提示词里 | `CORE_RULES` 字符串常量 | 合并时整段被覆盖而不自知 | 07-14 "修复 CORE_RULES 重复声明导致的规则丢失"，且在之后的导入中反复出现 |
| 从正文抽取事实 | 记忆 Agent 读散文 | 散文本身模糊，抽取有误 | 基线中无法测（没有矛盾检测） |

【判断】B 类不需要新算法，需要换结构：协议与正文分两次调用或用结构化输出；提示词做成独立文件并有渲染测试；事实尽量在"散文之前"就确定（见 §3 新方法 1）。

### C 逆训练偏好——提示词打不赢的仗

| 目标 | 模型的天然倾向 | 1.x 的尝试 | 结果 |
|---|---|---|---|
| 反谄媚：世界有阻力 | 顺着用户 | 07-10 双阶段 GM：先由裁判定 NPC 态度与检定，叙事者只执行 | 【事实】记忆里记为"治谄媚的根"——**这是唯一一次结构性解法，也是公认有效的一次** |
| 反雷同 / 起名不俗 | 收敛到高频表达（众数） | 07-11 起"写死提示词必雷同"，改为从作品库随机抽样；08-23 命名改用 Verbalized Sampling，模型给候选、程序避开众数 | 【事实】有效的都是"把随机性搬到程序侧"，而不是"请你多样化" |
| 反谜语人 / 反全员侦探 | 每条规则都被当成本轮要完成的任务 | 07-11 提示词大瘦身 | 【事实】用户反馈"最初没那么多提示词的版本反而自然" |
| 不替玩家决定 | 小说写法习惯替主角抒情、反应、做小动作 | 主权规则 + 主权守卫事后改写 | 【事实】守卫约 5% 回合触发；08-24 守卫把"执行玩家意图"误判为"替玩家做决定"（7d350cb） |

【判断】C 类的规律很清楚：**"多写一条禁令"每次都失败或带来副作用；"把决定挪到散文之外"每次都有效。** 继续在提示词里加约束是收益递减的。

### D 口味问题——规则写不出来

节奏、详略、"无聊不无聊"、铺垫好不好、有没有小说感。

- 【事实】这是 1.x 后期修改最密集的区域：提交说明里"穿越"出现 45 次、"冲突"39 次、"重复"38 次。`QUALITY_METRICS.md` 记录了截至 08-24 的八轮 *玩家玩 → 报告 → 改 → 再玩* 循环（原话："玩家在充当测试环境"），其中 08-22 至 08-23 被记录的 5 句玩家反馈有 4 句是穿越推进慢、1 句是"非常之无聊"。
- 【事实】详略的判据改过两次：先按阶段，08-23 改成"有没有冲突"（41362f0）。
- 【判断】今天的讨论给出了原因：**"有没有冲突才对"取决于这个故事的大纲**，日常故事本该多数幕无冲突。1.x 没有记录故事意图，于是只能用全局规则去猜——猜错一次加一条规则，这就是规则增长的引擎。我 10-28 提出的"最长连续无冲突幕 ≤ 2"犯的是同一个错误。
- 【判断】这类问题用任何更聪明的规则都解决不了，因为"对不对"的标准不在规则里，在**每局的意图**和**玩家的口味**里。

### E 自相矛盾——不是难，是不可能

- 【事实】33b9f6c："迁移阶段被两条矛盾指令锁死：**只有模型违抗指令时才会前进**。"
- 【事实】d599044："找到「反复修不好」的真正原因：规划器把玩家选定的前提当成了不该强推的钩子。"——玩家在开局选了"穿越"，但"不替玩家做决定"和"不强推钩子"的规则让系统不敢让穿越发生。
- 【判断】这是互动叙事的经典矛盾（计划要推进 vs 玩家要自由）以规则冲突的形式出现。没有任何模型能同时满足两条互斥指令；1.x 每次都是靠局部补丁让其中一条暂时失效。
- 已解决一半：10-28 定下了 **可靠性 > 主权 > 小说** 的优先级。还缺的一半是"玩家在开局做的选择，算不算对后续事件的授权"——这是产品决策，不是算法问题。

### 成本约束（不是墙，是预算）

【事实】每回合 2.63 次模型调用、约 1.47 万 token、中位 9.3 秒。每加一个检查 Agent 都加延迟。任何新方法都要回答"多花的调用换来了什么"。

## 3. 可能打破瓶颈的新方法（均为【假设】）

按"解决哪类问题"排列。每一项都需要在 2.0 原型里用回放验证，不能直接当结论。

### 新方法 1：事件层与文字层分离（针对 C、D、E）

先由规划/裁定产出本回合**结构化事件**——谁做了什么、NPC 什么态度、玩家的哪个动作产生了什么后果、本幕的张力预算——程序校验后，写手只负责把这些事件写成文字。

- 主权变成程序可查的问题：事件里出现玩家没输入的玩家动作 → 直接拦截，不再靠守卫读散文去猜。
- 冲突、铺垫变成可记账的问题：本幕计划了几个冲突事件、埋了哪条伏笔、兑现了没有。
- 依据：1.x 唯一公认有效的反谄媚手段（07-10 双阶段 GM）就是这个思路的雏形；经典的互动戏剧系统也把"剧情节拍"与"表层文字"分开管理。
- 风险：多一次调用；文字可能变得像"照单念"，失去即兴感。需要 A/B。

### 新方法 2：故事意图作为一等数据（针对 D）

每局有一份结构化意图：基调、长期承诺与人物目标（长期层），以及眼前 2–4 回合的场景预算——冲突强度、详略、信息揭示（眼前层）。中篇额外有隐藏候选结局。

- 节奏从"规则猜"变成"对照意图测偏差"——这是可定义的。
- 意图本身由规划器生成，玩家可通过少量旋钮（基调、节奏偏好）影响。
- 依据：用户 10-28 的判断"有没有冲突要看大纲"；综述 §1 的两层规划结构与 §6 "压力是场景预算"。

### 新方法 3：随机性留在程序侧（针对 C，已部分验证）

凡是"要多样、不要俗套"的东西——起名、开局、NPC 性格、事件类型——由程序从外部分布（研究库、候选列表）抽样，或让模型给多个候选后由程序避开众数，模型只负责写。

- 依据：07-11 起的数据驱动开局、08-23 的 Verbalized Sampling 命名，都是 1.x 里少数没有反复返工的改动。

### 新方法 4：玩家信号闭环（针对 D）

在游戏里加一个极轻的反馈：每章结束打分 + 可选一句话。每局自动变成带标注的数据。

- 用途一：校准自动指标（现在只靠 6 句玩家原话）。
- 用途二：在几个提示词/参数版本之间按反馈选优，而不是靠"玩一局、凭感觉改"。
- 风险：只有一个玩家，样本小，需要很多局才有统计意义。

### 新方法 5：候选生成 + 程序筛选（针对 C，代价高）

关键回合生成 2–3 个候选，用程序可算的条件（事件一致性、意图偏差、众数回避）选一个。综述里 Re³ 用过重排序。代价是调用数和延迟成倍增加，只适合开局、章节转折这类少数回合。

### 明确不在范围内

微调 / 偏好优化可以直接改变模型的训练倾向，是 C 类问题最根本的解法；但产品定义已选定"以云端大模型为准"，且是否能对所用模型做微调未核实。记为将来选项，2.0 不依赖它。

## 4. 对 2.0 的结论

1. **不再用提示词对抗模型偏好。** 发现自己要加一条"不要……"时，先问：这个决定能不能挪到散文之外、交给程序或结构化事件？
2. **不再用规则定义口味。** 节奏、冲突、详略由每局的意图数据决定，好坏用"偏离意图"和玩家反馈来衡量。
3. **矛盾在产品层解决。** 优先级已定；下一步要定"开局选择是否构成授权"。
4. **2.0 的核心架构问题因此变成**：意图（规划）→ 事件（裁定 + 程序校验）→ 文字（写手）→ 记账（程序）这条链如何切分，每一段由谁负责、交付什么。
