# 标准开发生命周期

以后所有工作都按阶段推进。每个阶段都有产物、入口条件、出口条件和停止条件；未满足出口条件时，不进入下一阶段，也不通过临时提示词掩盖结构问题。

## Phase 0：基线冻结与可重复运行

**目标**：知道现在是什么，不在移动靶上开发。

### 产物

- 当前版本号和 Git 基线。
- 组件清单、API 清单、数据表清单。
- 10 个固定多回合回放场景（详见 [REPLAY_BASELINE.md](./REPLAY_BASELINE.md)）。
- 关键 UX 验收：新局、读档、SSE、Enter、选项、撤销、后端离线。
- 每个回放的输入、状态、输出、调用次数、耗时和错误指标。

### 入口条件

- 能在本机启动后端并打开主界面。
- 能导出调试记录和存档。

### 出口条件

- 同一输入在固定随机种子/固定模型响应下可重放。
- 明确哪些失败是当前已知缺陷，哪些是环境问题。

### 禁止事项

- 不新增 Agent。
- 不大改提示词。
- 不拆前端文件。

## Phase 1：领域模型与契约冻结

**目标**：先定义游戏是什么，再决定代码放哪里。

### 必须冻结的对象

`GameSession`、`Turn`、`GameState`、`CanonFact`、`EventRecord`、`Commitment`、`NpcBelief`、`CharacterDynamicState`、`SceneContract`、`ActionOption`、`StatePatch`、`AgentRun`。

每个对象需要：

- 字段和类型；
- 来源和可信度；
- 生命周期；
- 版本和迁移方式；
- 谁可以创建、修改、废弃；
- API/存档/监视器如何表示。

### 出口条件

- Pydantic schema、数据库模型和前端类型没有关键字段漂移。
- 失败、重试、取消、部分成功的语义已写明。
- 旧存档迁移规则和兼容期限已决定。

## Phase 2：服务端 Game Loop

**目标**：把回合的权威编排从前端逐步移到后端。

顺序：

1. 创建 `TurnService`，先复用现有服务；
2. 将输入、状态版本、检索结果、模型调用、patch、提交结果写入一回合记录；
3. 增加幂等键和状态版本检查；
4. 前端改为订阅回合事件和 SSE，而不是自行决定提交顺序；
5. 保留旧接口作为兼容层，直到回放和浏览器验收通过。

### 出口条件

- 断网/重试不会重复应用状态。
- 任何回合都能解释“用了哪些事实、哪个 SceneContract、哪个 patch”。
- 前端仅负责展示和输入，不再直接修改权威状态。

## Phase 3：记忆与状态质量

**目标**：解决忘记、混淆和 NPC 全知，而不是先追求更多剧情花样。

顺序：

1. 事实有效区间和冲突状态；
2. 事件与事实的因果引用；
3. NPC belief 可见性过滤；
4. 承诺生命周期；
5. 检索 trace 和被排除内容；
6. 服务端章节摘要和回放恢复。

### 出口条件

- 20 回合承诺场景、秘密传播场景、关系恢复场景均能稳定回放。
- 检索召回错误和不该知道次数有明确指标。
- 事实抽取失败不会阻塞正文，也不会覆盖旧正史。

## Phase 4：场景规划与叙事写作

**目标**：让 Planner 规划“当前可执行场景”，而不是写一份会强迫写手的长篇大纲。

### 规则

- Planner 只在开局、场景切换、契约到期或高风险事件触发。
- Writer 每回合只看到公开 SceneContract，不看到 private cause。
- `affordances` 是可能行动，不是强制事件。
- 玩家拒绝后，旧承诺必须失效或转入暂停，不能换皮重发。
- 规划失败时使用兼容场景卡，不阻塞正常流式回合。

### 出口条件

- 同一场景不同玩家输入能产生状态、关系或事件差异。
- 低压场景五回合不自动升级为阴谋/追杀。
- planner 额外调用只发生在有理由的回合。

## Phase 5：规则系统与可玩性

**目标**：把需要一致性的玩法从模型提示词中移到程序。

优先顺序：

1. 资源/金钱/背包/装备；
2. 时间、位置和移动可行性；
3. 对话/交易/承诺；
4. 检定和失败代价；
5. 任务生命周期；
6. 复杂战斗、地图和经济模拟。

每个规则必须有纯函数、单元测试、失败边界和回放场景。没有固定玩法需求时不扩展规则。

## Phase 6：前端模块化与兼容迁移

**目标**：保留成熟体验，同时降低单文件维护成本。

迁移顺序：

1. 把 API client 抽出；
2. 把 GameStore/存档序列化抽出；
3. 把回合控制器抽出；
4. 把流式渲染器、选项解析器和监视器抽出；
5. 最后再拆 UI 组件和样式。

每一步都必须让旧 `index.html` 入口可运行，并通过不可回退验收。不要先换 React/Vue，再试图找回旧功能。

## Phase 7：评价、发布和维护

### 固定评价指标

- 关键事实错误数；
- NPC 未授权知识次数；
- 承诺遗忘/换皮重发次数；
- 玩家越权次数；
- 状态 patch 错误数；
- 无关描写比例；
- 选项有效率；
- 首 token 延迟、总回合延迟、模型调用次数；
- SSE、Enter、存档和后端离线回归通过率。

### 发布门

发布前必须同时通过：

1. Python 单元和接口测试；
2. schema/数据库迁移测试；
3. 固定多回合回放；
4. 浏览器冷启动和关键交互；
5. 启动器安装/启动/停止/异常恢复；
6. API Key、存档和调试导出脱敏检查；
7. README、变更日志和回滚说明。
